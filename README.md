# space

Веб-интерфейс, который показывает, как расходуется место на сервере с геномными
данными. Показывает, кто и чем занимает диск, что можно сжать или удалить и как
быстро заканчивается место.

Нужны только права `sudo ncdu`. Сканирование делает `ncdu -x -e -o -`: это
полное дерево с владельцем, правами и mtime каждого файла. Всё остальное
(разбор, индекс, веб-интерфейс) работает от обычного пользователя. Интерфейс
слушает только `127.0.0.1` и открывается с ноутбука через SSH-туннель.

```
sudo ncdu -x -e -o - /data | gzip   →   snapshots/*.ncdu.json.gz   →   space serve   →   ssh -L   →   браузер
```

## Быстрый старт

На сервере с данными:

```bash
git clone <repo> space && cd space
make build                     # нужен Go ≥ 1.22; без Go: скопируйте dist/space-linux-amd64 (make dist)

# 1. Снимок, вручную, внутри tmux: 20+ млн файлов сканируются долго, sudo спросит пароль один раз
tmux new -s scan
./scripts/collect.sh /data               # можно несколько путей: /data /home

# 2. Интерфейс (тоже в tmux, чтобы жил после выхода)
./bin/space serve -dir ./snapshots       # слушает 127.0.0.1:8377
```

На Mac:

```bash
ssh -N -L 8377:127.0.0.1:8377 <genome-server>
open http://localhost:8377
```

Новые снимки сервер подхватывает сам: каталог перечитывается при каждом
открытии страницы и раз в 30 секунд. Индексация идёт в фоне, её прогресс
показан на странице «Снимки».

## Что пишет `scripts/collect.sh`

Для каждого пути `<id> = <host>__<путь>__<время>`:

| файл | откуда | зачем |
|---|---|---|
| `<id>.ncdu.json.gz` | `sudo ncdu -x -e -0 -o - PATH \| gzip -1` | дерево файлов с uid/mode/mtime |
| `<id>.ncdu.json.gz.part` | то же, пока идёт сканирование | UI показывает «идёт сканирование» |
| `<id>.df` | `df -B1 -P PATH` (без sudo) | объём и заполненность диска, прогноз |
| `<id>.passwd`, `<id>.group` | `getent passwd/group` | имена вместо uid, поиск удалённых пользователей |

Переменные: `OUT=` задаёт каталог снимков, `NCDU_ARGS="--exclude .snapshot"`
добавляет исключения. `MODE=file` нужен, если `sudo ncdu -o -` не пишет в pipe:
тогда ncdu пишет файл сам, а `sudo chown` возвращает его вам. `SUDO=` позволяет
сканировать без sudo то, что вам и так доступно.

После сканирования скрипт проверяет архив (`gzip -t`). Битый снимок не
публикуется. Если снимок битый или обрезан, интерфейс показывает ошибку и не
выдаёт частичные данные за полные.

## Разделы интерфейса

- **Обзор.** Заполненность диска (по df). Плитки: что можно сжать, публичные
  данные NCBI/ENA, референсы, временные файлы, conda, данные старше года,
  файлы удалённых пользователей, дубликаты. Топ владельцев и типов файлов,
  возраст данных, крупнейшие каталоги.
- **Проводник.** Treemap и таблица подкаталогов с владельцем, датой последнего
  изменения и меткой группы данных; крупные файлы в каталоге.
- **Владельцы.** Сколько занимает каждый uid, какая доля старше года, где лежат
  его данные. Для удалённых пользователей генерируются команды
  `sudo chown -R новый 'путь'`. Сам интерфейс их не выполняет.
- **Типы файлов.** FASTQ/BAM/CRAM/VCF/FASTA/pod5/… с оценкой, сколько
  освободит сжатие, и примером команды.
- **Что освободить.** Сжатие; публичные данные (accession SRR/ERR/DRR/GCA_/GCF_/PRJNA
  в пути) с командами для повторного скачивания; референсы; Nextflow `work/`,
  `.snakemake`, tmp и core dumps; conda; корзины; каталоги, которые давно не
  менялись; дубликаты.
- **Динамика.** Занятое место по снимкам серии, скорость роста, прогноз
  заполнения, изменения по владельцам. Сравнение двух снимков показывает, в
  каких каталогах возник рост.

## Ограничения и эвристики

- Размеры считаются как занятые блоки (`dsize`); файлы с несколькими жёсткими
  ссылками учитываются один раз.
- «Не менялось» означает mtime. Время последнего чтения ncdu не видит.
- Коэффициенты сжатия — типичные значения, а не измерения на ваших данных.
  В интерфейсе они подписаны как «оценка».
- Публичные данные, референсы и временные файлы определяются по именам файлов и
  каталогов. Это кандидаты на проверку, а не приговор.
- Мелкие файлы по отдельности не хранятся: индекс держит суммы по каталогам и
  200 000 крупнейших файлов. Поэтому индекс снимка на десятки миллионов файлов
  занимает сотни мегабайт, а не гигабайты.
- Дубликаты ищутся по имени и размеру среди крупнейших файлов, содержимое не
  сравнивается.

## Производительность (замеры на этом сервере, 12 ядер)

| снимок | файлов | каталогов | индексация | пик памяти | индекс на диске |
|---|---|---|---|---|---|
| реальный ncdu 1.15.1, `/mnt/alpha/claude` | 1,54 млн | 52 тыс | 9,4 с | 187 МБ | — |
| синтетический (`tools/synth`) | 3,0 млн | 122 тыс | 12,8 с | 327 МБ | 17 МБ |

Индексация идёт однопоточно, её скорость ограничена распаковкой gzip и
разбором JSON: примерно 4–7 с на миллион файлов. Для 20–30 млн файлов
ожидается 2–4 минуты и 1–2 ГБ памяти в пике. Это экстраполяция, на таком
объёме не измерялось. Сервер держит в памяти два последних открытых индекса
(`-keep`). Само сканирование `ncdu` на реальном диске на порядки медленнее
индексации: на `/mnt/alpha/claude` (1,5 млн файлов) оно заняло около минуты.

## Разработка

```bash
make test      # go vet + go test (парсер, классификатор, индекс, хранилище, API)
make dist      # статические бинарники linux-amd64/arm64 и darwin-arm64
go run ./tools/synth -files 5000000 -out snapshots/synth__data__20260101-000000.ncdu.json.gz
```

Устройство:

- `internal/ncdu` — потоковый парсер формата экспорта ncdu, работает в
  ограниченной памяти.
- `internal/classify` — типы файлов, accession, временные каталоги.
- `internal/index` — дерево каталогов с суммами по поддеревьям, разбивки по
  владельцам, типам и группам, выборки (frontier, stale, diff).
- `internal/store` — обнаружение снимков, фоновая индексация, кэш в
  `snapshots/.space-cache/`.
- `internal/server` — JSON API.
- `web/static` — интерфейс на чистом JS без внешних зависимостей, встроен в
  бинарник.
